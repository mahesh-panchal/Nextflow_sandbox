# Nextflow Workflow Development Protocol
**Minimum supported Nextflow version: 25.10.0**

---

## STANDING ORDERS — Read Before Any Other Action

These rules override every other instruction in this document.

```
SO-1  AUDIT FIRST.      List directory contents before asking any question.
SO-2  DECLARE.          Write out your findings explicitly before proceeding.
SO-3  NO FILES.         Do not create or modify any file until the user confirms
                        the Phase 0.7 summary.
SO-4  COMPLETE PHASES.  Finish each phase fully before starting the next.
SO-5  PHASE 8 WINS.     If any instruction conflicts with Phase 8 (Absolute
                        Rules), Phase 8 takes precedence.
SO-6  TRACK STATE.      Maintain these three values at all times:
                        PATH_LABEL, CMD_PREFIX, STAGES.
SO-7  CHECKPOINTS.      At every >> CHECKPOINT marker, state PATH_LABEL,
                        CMD_PREFIX, and STAGES before writing anything else.
SO-8  RUN COMMANDS.     Run all commands directly using available tools.
                        After each command:
                        (a) Report the relevant output or result.
                        (b) If the command succeeded, continue to the next step.
                        (c) If the command failed, show the full error output
                            and ask: "How would you like to proceed?"
                        Do not silently retry. Do not infer causes. Wait for
                        explicit user instruction.
SO-9  NO GHOST FILES.   Never manually reproduce files generated by a tool
                        command (nf-core pipelines create, nf-core modules
                        install, pixi init, etc.). If such a command fails,
                        report the full error and ask how to proceed.
SO-10 MISSING TOOLS.    If a command fails because a tool is not found on PATH,
                        classify it using SO-13 first.
                        - DEVELOPMENT TOOL + CMD_PREFIX = pixi run:
                          run `pixi add <toolname>`, confirm success, retry.
                        - DEVELOPMENT TOOL + CMD_PREFIX = (none):
                          report the missing tool and ask how the environment
                          is managed. Wait before retrying.
                        - PIPELINE TOOL: do not install via pixi. See SO-13.
SO-11 SCAFFOLD THEN     Development proceeds in two distinct phases:
      IMPLEMENT.
                        SCAFFOLD PHASE — the model writes all stubs, wires
                        all subworkflows, wires the main workflow, writes all
                        nf-test files, and runs `nextflow run -stub` to
                        validate the complete structure in one pass. Nothing
                        is considered implemented during this phase. The
                        scaffold phase ends when:
                          (a) `nextflow lint` passes on all .nf files, and
                          (b) `nextflow run <WORKFLOW_FILE> -stub -profile test`
                              completes without error.
                        The programmer confirms the scaffold before
                        implementation begins.

                        IMPLEMENTATION PHASE — stubs are replaced with real
                        implementations one module at a time. Each module's
                        real nf-test must pass before that module is complete.
                        Each stage's subworkflow nf-test must pass (real
                        execution, not stub) before that stage is done. No
                        stage is complete until all its modules and its
                        subworkflow nf-test pass.

SO-12 PLAN FIRST.       A PLAN.md must exist in the project root before any
                        .nf file is written or modified. PLAN.md is updated
                        after every completed step. It is the authoritative
                        record of development state.

SO-13 TOOL ISOLATION.   Two distinct categories of tools exist:

                        PIPELINE TOOLS — tools that execute inside Nextflow
                        process tasks (samtools, fastp, bwa, STAR, gatk,
                        bcftools, multiqc, etc.). These MUST be declared in
                        the process `conda` or `container` directive. They
                        must NEVER be installed via pixi.

                        DEVELOPMENT TOOLS — tools used by the development
                        environment (nextflow, nf-core, nf-test, jq,
                        pre-commit, git, etc.). These CAN and SHOULD be
                        managed by pixi when CMD_PREFIX = pixi run.

                        Classify the tool before resolving any missing-tool
                        error. Never install a pipeline tool into pixi.

SO-14 LINT FIRST.       Before running nf-test on any module or subworkflow,
                        run `nextflow lint <file>` on that file first.
                        - Errors must be fixed before testing proceeds.
                        - Warnings do not block testing but must be recorded
                          in PLAN.md under Notes and reviewed with the user.

SO-15 MISSING           If any process-to-process connection has an output
      CONNECTIONS.      format that does not obviously match the downstream
                        input format, STOP IMMEDIATELY. Do not infer a
                        conversion. Present the gap:

                        "I found a connection gap:
                          Upstream:   [PROCESS_A] emits [format / file type]
                          Downstream: [PROCESS_B] expects [format / file type]
                        How should this be handled?
                          (a) The formats are compatible — just needs
                              documenting correctly.
                          (b) There is a missing intermediate tool or process
                              step not included in the design.
                          (c) A custom script or file manipulation step is
                              needed to bridge the two."

                        Wait for the user's answer. Record the resolution in
                        PLAN.md. Never write bridging code without explicit
                        instruction.

SO-16 COMMIT CADENCE.   Commit to git at each of these points only:
                        - After PLAN.md is written:
                          "docs: add development plan"
                        - After scaffold passes -stub validation:
                          "feat: scaffold complete — all stubs wired and -stub passing"
                        - After each nf-core module installed:
                          "feat: install nf-core/<tool>/<subcommand>"
                        - After each nf-core module patched:
                          "fix: patch nf-core/<tool>/<subcommand> — <reason>"
                        - After each local module real nf-test passes:
                          "feat: implement <tool> module — nf-test passing"
                        - After each subworkflow nf-test passes (real):
                          "feat: <stage> subworkflow — nf-test passing"
                        - After main workflow end-to-end test passes:
                          "feat: end-to-end test passing"
                        - After PLAN.md is updated mid-development:
                          "docs: update PLAN.md — <what changed>"

SO-17 MODULE INFO.      For every local module, the programmer must supply
                        the following before the real script: block can be
                        written:
                        (a) Exact conda package specification
                        (b) Docker container URI with full tag and build hash
                        (c) Singularity container URI
                        (d) Tool CLI usage example or link to documentation

                        Never guess, infer, or construct these values.
                        A stub placeholder must be used until all four are
                        supplied. See Phase 3.5.11 for how the programmer
                        finds this information.

                        This rule does not apply to nf-core installed modules.

SO-18 TODO MARKERS.     Every section of generated code or configuration that
                        the programmer must review or complete is marked with
                        a structured TODO comment. Three levels exist:

                        // TODO [REQUIRED]: <description>
                        //   Must be filled in before this module will run.
                        //   The pipeline will error if left as-is.

                        // TODO [REVIEW]: <description>
                        //   Verify this is correct for your specific tool
                        //   or use case. May work as-is but should be checked.

                        // TODO [FILL-IN]: <description>
                        //   A specific value the programmer provides, e.g.,
                        //   ext.args, output file pattern, version command.

                        Programmers should search for "TODO" in all generated
                        files to find every item requiring attention.
```

Inform the user of the finding and ask them to confirm.

**What each path means:**

| | `[PATH-A]` | `[PATH-B]` | `[PATH-C]` |
|---|---|---|---|
| Structure | nf-core template | Custom, you design it | Custom, you design it |
| Main workflow file | `workflows/<name>.nf` | `main.nf` | `main.nf` |
| `nf-core modules install` | Yes | Yes | **No** |
| `nf-core lint` | Required at each stage | Not required | Not required |
| `nextflow_schema.json` | `nf-core schema build --no-prompts` | Maintain manually | Maintain manually |
| Git | Auto by `nf-core pipelines create` | Your choice | Your choice |

If **ASK USER**, ask Q1 (nf-core compliant?) → Q2 (nf-core registry modules?) → Q3 (fully custom?).

### 0.2b In-Progress Pipeline Detection

*Run immediately after confirming PATH_LABEL.*

**If `PLAN.md` is present:** read it in full. Extract PATH_LABEL, CMD_PREFIX, STAGES, REPORTING, scaffold status, and all module/test statuses. Check the Module Specifications table for what info is still pending.

**If `PLAN.md` is absent**, evaluate:

```
IN-PROGRESS CHECKLIST (only when PLAN.md is absent)
─────────────────────────────────────────────────────────────────
[ ] modules/local/ contains at least one .nf file     yes / no
[ ] modules/nf-core/ contains installed modules        yes / no
[ ] subworkflows/local/ contains at least one .nf file yes / no
[ ] workflows/ contains at least one .nf file          yes / no  (PATH-A)
[ ] main.nf contains a workflow { } block              yes / no
[ ] tests/ contains at least one .nf.test file         yes / no
[ ] tests/nextflow.config exists                       yes / no
[ ] nf-test.config exists                              yes / no
─────────────────────────────────────────────────────────────────
```

- All no + no PLAN.md → bootstrap done, no development started → Phase 0.3.
- Any yes + no PLAN.md → ask the user questions 1–4 (what does it do, last step, what's broken, do you have module info ready?). Determine STAGES and CMD_PREFIX from codebase. Present Resume State, then write PLAN.md before resuming.

```
RESUME STATE
─────────────────────────────────────────────────────────────────
PATH_LABEL:                [value]
CMD_PREFIX:                [pixi run / (none)]
STAGES:                    [list or "unconfirmed"]
REPORTING:                 [multiqc / notebook / none / "unconfirmed"]
Main workflow file:        [WORKFLOW_FILE]
Scaffold status:           [not started / in progress / complete]
tests/nextflow.config:     [present / absent — absent will cause nf-test failures]
Module info pending:       [list of local modules awaiting info]
Local module stubs:        [module → stub present / missing]
Local module real tests:   [module → pass / fail / not started]
Subworkflow real tests:    [subworkflow → pass / fail / not started]
Last work:                 [user summary]
Known issues:              [user summary or "none"]
Resume point:              Phase [N] — [description]
─────────────────────────────────────────────────────────────────
```

**Resume point rules:**

| Condition | Resume at |
|---|---|
| PLAN.md absent | Phase 2 — write the plan |
| `tests/nextflow.config` absent | Phase 5.0 Step 7 — create it immediately |
| Scaffold not complete | Phase 5.0 — complete the scaffold |
| Scaffold complete, module info pending | Programmer handover — request module info |
| Module info supplied, real test failing | Phase 5.1 Step 4 — fix the test |
| All module tests pass, subworkflow test failing | Phase 5.2 — fix subworkflow test |
| All subworkflow tests pass, end-to-end failing | Phase 6 |

>> CHECKPOINT: State PATH_LABEL, CMD_PREFIX, STAGES before writing anything.

### 0.3 Questions by Path

Skip questions whose answers are already known.

**If the user provides a design artifact** (mermaid diagram, flowchart, process list), parse it first. Extract every process and every directed connection. Proceed to Phase 0.4 and 0.4b before asking remaining questions.

**Reporting question (all paths):**

> "What will this pipeline use for quality reporting?
> (a) MultiQC — aggregates tool QC output into a single HTML report.
> (b) Custom notebook (Quarto or Marimo) — a notebook outside the pipeline
>     reads output files; the pipeline collects designated metric files.
> (c) None — the pipeline produces output files only."

Record: **REPORTING = multiqc / notebook / none**

If multiqc: which tools produce MultiQC-compatible output?
If notebook: which log/metric files should be collected?

#### Questions Set A — `[PATH-A]`

1. **Pipeline name** — must match `^[a-z]+$`. Record: **PIPELINE_NAME**
2. One or two sentence description.
3. Inputs?
4. Expected outputs?
5. Tools needed? For each: nf-core module known to exist?
6. Any in-house scripts or tools unavailable in Bioconda/Biocontainers?
7. Where will this pipeline run?
8. Development shell managed by Pixi? (Yes → `CMD_PREFIX = pixi run`; No → `CMD_PREFIX = (none)`)
9. Reporting question (above).

Sets B and C follow the same pattern without the pipeline name question (Set C also omits the nf-core module question and does not add `nf-core` to pixi).

### 0.4 Stage Planning

3. For each stage: which tools?
4. For each stage except the last: output index CSV columns?
5. Shared or per-stage samplesheet schema?

```markdown
### Test file layout

```
tests/
├── nextflow.config          ← REQUIRED global test config
├── main.nf.test             ← end-to-end pipeline test (lives here, not in a subdirectory)
├── create_test_data.sh

│   ├── nextflow.config      ← per-test ext.args binding
│   └── main.nf.test

```
### Immediate actions (in order)

**Step 1 — Review the scaffold**
Run: `nextflow run <WORKFLOW_FILE> -stub -profile test`
Confirm the output directory structure matches your expectations.
Check that stage connections look correct.

**Step 2 — Gather module information**
For each module marked ⏳ in Module Specifications above:
  - Find conda spec, Docker URI, Singularity URI, CLI usage (see Phase 3.5.11)
  - Paste info into the chat and the model will implement the module

**Step 3 — Implement modules (one at a time, any order)**
For each module, after providing info:
  - Model fills in directives and script: block
  - Run: `nextflow lint modules/local/<tool>/main.nf`
  - Run: `nf-test test tests/modules/local/<tool>/main.nf.test --profile docker`
  - Fill in the TODO assertion sections in the nf-test file
  - Commit when test passes

**Step 4 — Run subworkflow tests (after all modules in a stage pass)**
  Run: `nf-test test tests/subworkflows/local/<stage>/main.nf.test --profile docker`

**Step 5 — Run end-to-end test (after all subworkflow tests pass)**
  Run: `nf-test test tests/main.nf.test --profile docker`

**Step 6 — Replace synthetic test data**
  See Synthetic Test Data table below.
```

### 3.2 Process Anatomy — Fully Implemented Local Module

Use this template only when the programmer has supplied all four values required by SO-17.

```nextflow
process TOOLNAME_SUBCOMMAND {
    tag "${meta.id}"
    label 'process_medium'
    ext prefix: "${meta.id}", args: '', when: true

    conda "bioconda::toolname=1.2.3"
    container "${ workflow.containerEngine == 'singularity' && !task.ext.singularity_pull_docker_container ?
        'https://depot.galaxyproject.org/singularity/toolname:1.2.3--h1234567_0' :
        'biocontainers/toolname:1.2.3--h1234567_0' }"

    input:
    tuple val(meta), path(reads, arity: '1..*')
    path  reference

    output:
    tuple val(meta), path("*.bam"),                                                                     emit: bam
    tuple val(meta), path("*.log"),                                                                     emit: log
    tuple val("${task.process}"), val('toolname'), eval('toolname --version 2>&1 | head -1'),          emit: versions_toolname, topic: versions

    when: task.ext.when

    script:
    def args   = task.ext.args
    def prefix = task.ext.prefix
    """
    toolname subcommand \\
        ${args} \\
        --threads ${task.cpus} \\
        --output ${prefix}.bam \\
        ${reads}
    """

    stub:
    def prefix = task.ext.prefix
    """
    touch ${prefix}.bam ${prefix}.log
    """
}
```

**Key points:**
- `ext` defaults guarantee values — no `?: ''` fallbacks in `script:`
- `when: task.ext.when` with `ext when: true` → always runs unless config overrides
- `eval()` + `topic: versions` → global channel, no wiring required anywhere
- `arity: '1..*'` on required path inputs; `'0..1'` or `'0..*'` on optional ones
- Installed nf-core modules use a different internal style — do not change it, patch instead

### 3.6 Essential Channel Operators

All closure parameters must be named. Never use implicit `it`. Prefix unused ones with `_`.

```nextflow
ch_bam.join(ch_bai, by: [0])
ch_samples.combine(ch_reference)
ch_reads.map { meta, reads -> [ meta + [processed: true], reads ] }

    paired: !meta.single_end
```

`collect()` on empty → no emission; flattens nested lists.
`toList()` on empty → emits `[]`; preserves nesting.

### 3.7 Variable Scoping in Workflow Blocks

**Binding variables for inter-stage results** — initialise to `null` before conditionals; do NOT use `def` on the assignment inside the `if` block:

```nextflow
workflow {
    main:
    // Initialise binding variables — visible across all if blocks
    def clean_out  = null   // holds subworkflow result, or stays null
    def align_out  = null

    // Use null for process/subworkflow results
    // Use channel.empty() for channel accumulators
    def ch_cleaned_index = channel.empty()   // accumulates index rows
    def ch_multiqc_files = channel.empty()   // accumulates multiqc inputs

    if ("clean" in params.stages) {
        // No def here — assigns to the binding variable declared above
        clean_out        = CLEAN_DATA(ch_reads)
        ch_cleaned_index = clean_out.reads.map { meta, reads -> /* ... */ }
    }

    if ("align" in params.stages) {
        align_out = ALIGNMENT(
            clean_out != null ? clean_out.reads : ch_reads,  // != null, not truthiness
            ch_genome_fasta
        )
    }
}
```

**Summary:**

| Context | Use `def`? |
|---|---|
| Closure parameter variable | Always |
| Variable inside `script:` block | Always |
| Process/subworkflow result binding in workflow scope | Never — pre-declare as `null` |
| Channel accumulator in workflow scope | `def ch = channel.empty()` |
| Temporary variable scoped to one block | Yes |

### 3.8 Static Typing Readiness

| Pattern | Avoid | Use instead |
|---|---|---|
| Channel assignment | `.set { ch }` | `ch = channel.of(...)` |
| Process output in pipeline code | `PROCESS.out.bam` (unassigned) | `r = PROCESS(ch); r.bam` |
| Subworkflow output | `SW.out.reads` (unassigned) | `sw = SW(ch); sw.reads` |
| Pipe operator | `ch \| PROCESS \| view` | `r = PROCESS(ch); r.view()` |
| Cross-product input | `each method` qualifier | `.combine(methods)` |
| Iteration | `for (s in list)` | `channel.fromList(list)` |
| Implicit variable | `.map { it * 2 }` | `.map { val -> val * 2 }` |
| Switch | `switch (x) { ... }` | `if/else` or map lookup |
| Import | `import groovy.json.JsonSlurper` | `new groovy.json.JsonSlurper()` |
| Spread | `[meta, *files]` | `[meta] + files` |

**`.out` in pipeline code:** assign first. `r = PROCESS(ch)` then `r.bam`.
**`.out` in nf-test:** `process.out.xxx` and `workflow.out.xxx` are the nf-test API — correct inside `then { }`.

## Phase 3.5: Common Patterns Reference

### 3.5.1 `arity` Reference Table

| Situation | `arity` | Variable type | Accepts `[]`? |
|---|---|---|---|
| Exactly one file, required | `'1'` | `Path` | No |
| One or more, required | `'1..*'` | `List<Path>` | No |
| Zero or one, optional | `'0..1'` | `Path` or empty | Yes |
| Zero or more, optional | `'0..*'` | `List<Path>` | Yes |

Optional inputs that may receive `[]` must use `'0..1'` or `'0..*'`.

### 3.5.2 `join` vs `combine` Decision Table

| Situation | Operator |
|---|---|
| Two per-sample channels, same sample set | `join(by: [0])` |
| Per-sample + single shared reference | `combine` with value channel |
| Per-sample + per-sample reference | `join(by: [0])` |
| Every sample with every reference | `combine` with queue channel |

### 3.5.12 nf-test Script Path Resolution and Required Files

This section documents behaviours that are not obvious and have caused failures in practice.

#### Directory structure for tests

```
project-root/
├── nf-test.config             ← testsDir = "tests"
├── main.nf
├── modules/local/<tool>/main.nf
├── subworkflows/local/<stage>/main.nf
└── tests/
    ├── nextflow.config        ← REQUIRED — nf-test exits without this file
    ├── main.nf.test           ← pipeline test lives here, NOT in a subdirectory
    ├── create_test_data.sh
    ├── data/
    ├── modules/local/<tool>/
    │   ├── nextflow.config
    │   └── main.nf.test
    └── subworkflows/local/<stage>/
        ├── nextflow.config
        └── main.nf.test
```

#### `tests/nextflow.config` is mandatory

nf-test requires this file to exist. Without it, the framework exits immediately with:

```
Error: Test config file '.../tests/nextflow.config' not found
```

This file is the global test configuration loaded for **all** tests in the `tests/` directory. At minimum it can be empty, but it should define common process labels for fast local test execution:

```groovy
// tests/nextflow.config — global config loaded for ALL tests
params {
}

process {
    withLabel: 'process_single' { cpus = 1; memory = '1.GB'; time = '1.h' }
    withLabel: 'process_medium' { cpus = 2; memory = '4.GB'; time = '1.h' }
    withLabel: 'process_high'   { cpus = 4; memory = '8.GB'; time = '1.h' }
}
```

#### Script path resolution

nf-test resolves `script` paths relative to the `tests/` directory root (the value of `testsDir` in `nf-test.config`), not relative to the individual test file's location.

| Test file | Target `.nf` file | Correct `script` path |
|---|---|---|
| `tests/main.nf.test` | `main.nf` at project root | `"../main.nf"` |
| `tests/modules/local/<tool>/main.nf.test` | `modules/local/<tool>/main.nf` | `"../modules/local/<tool>/main.nf"` |
| `tests/subworkflows/local/<stage>/main.nf.test` | `subworkflows/local/<stage>/main.nf` | `"../subworkflows/local/<stage>/main.nf"` |

All paths use `../` to navigate from the `tests/` root up to the project root, then down to the target file.

**Pipeline tests must be placed directly in `tests/`**, not in a subdirectory. Placing a pipeline test in `tests/pipeline/main.nf.test` causes path resolution to behave differently and may not find the target file.

#### `workflow.trace.*` is not supported

Tracing is disabled by nf-test. Using `workflow.trace.succeeded()` or `workflow.trace.failed()` throws a runtime error:

```
java.lang.RuntimeException: Error: Tracing is disabled. `workflow.trace` is not supported.
```

Assert output file existence instead of trace counts.

#### Warnings from nf-core template modules

When running nf-test on a project that uses pixi or a local nf-core installation, warnings like the following may appear:

```
Warning: Module /path/to/.pixi/.../subworkflows/nf-core/utils_nextflow_pipeline/tests/main.function.nf.test:
  Dependency '.../subworkflows/nf-core/utils_nextflow_pipeline/main.nf' not found.
```

These are **harmless**. They come from nf-core template subworkflows installed in the pixi environment that have test stubs referencing their own source files. They do not affect your pipeline's tests.

```nextflow
        def new_meta = meta + [ single_end: !fastq_2 ]
        [ new_meta, reads ]
    }
}
```

## Phase 8: Absolute Rules

### Never Do These

| Rule | Applies to | Reason |
|---|---|---|
| Do not guess conda specs, container URIs, or build hashes | All | SO-17. Wrong values silently pull incorrect software. |
| Do not write a real `script:` block before module info is supplied | All | SO-17. Use stub until info is supplied. |
| Do not begin module implementation before the scaffold `-stub` run passes | All | SO-11. |
| Do not treat a module as done before its real nf-test passes | All | SO-11. |
| Do not treat a stage as done before its subworkflow real nf-test passes | All | SO-11. |
| Do not run nf-test without `tests/nextflow.config` present | All | nf-test exits immediately with an error if this file is absent. |
| Do not place the pipeline end-to-end test in a subdirectory of `tests/` | All | Script path resolution for `nextflow_pipeline` tests only works reliably when the test file is directly in `tests/`. |
| Do not use `workflow.trace.succeeded()` or `workflow.trace.failed()` | All | Tracing is disabled by nf-test — these throw a runtime error. Assert output file existence instead. |
| Do not run nf-test on a file with outstanding lint errors | All | SO-14. |
| Do not write any `.nf` file before PLAN.md exists | All | SO-12. |
| Do not install pipeline tools via pixi | All | SO-13. They come from `conda`/`container` directives. |
| Do not write nf-test files for installed nf-core modules | All | They have upstream CI tests. |
| Do not write bare `assert` statements in `then` blocks | All | All assertions must be inside `assertAll({ }, { })` — every assertion is evaluated and reported even if one fails earlier. |
| Do not snapshot unstable outputs (logs with timestamps, images, paths) | All | Snapshots of unstable content fail non-deterministically. Assert `.exists()` or `.name` instead. |
| Do not use `sanitizeOutput` on real implementation test outputs | All | `sanitizeOutput` is for stub tests. Real tests snapshot specific stable content. |
| Do not use `--update-snapshot` without reviewing the diff | All | Updating silently accepts any change, defeating the regression test. |
| Do not use `def` on inter-stage binding variables in workflow scope | All | Scopes them to the `if` block, breaking access from later stages. |
| Do not omit `def` inside closures and script blocks | All | Without it, variables leak globally and cause race conditions. |
| Do not use `arity: '1'` or `'1..*'` on optional path inputs | All | These reject `[]`. Use `'0..1'` or `'0..*'`. |
| Do not pass `null` to a process input | All | Use `channel.value([])` for absent optional path inputs. |
| Do not add logic to `main.nf` on PATH-A | PATH-A | Entrypoint only. All logic in `workflows/<name>.nf`. |
| Do not use hardcoded paths in the `output {}` block | All | Paths are relative to `params.outdir`. |
| Do not emit `multiqc_files` from a subworkflow unless REPORTING = multiqc | All | Unnecessary channel noise. |
| Do not access `.out` on an unassigned call in pipeline code | All | Assign first: `r = PROCESS(ch)` then `r.bam`. |
| Do not emit a versions channel from a subworkflow | All | `channel.topic('versions')` is global. |
| Do not set `publishDir` in `modules.config` when `output {}` is in use | All | Mutually exclusive. |
| Do not use `Channel.*` (uppercase) | All | Lowercase `channel.*` is current convention. |
| Do not use implicit `it` in closures | All | All parameters must be named. |
| Do not use `for` loops in workflow scope | All | Use channel operators. |
| Do not use `when:` for conditional process execution | All | Use `if` blocks or `filter`/`branch`. |
| Do not use a pipeline name outside `^[a-z]+$` | PATH-A | nf-core enforces this. |
| Do not manually edit `modules.json` | PATH-A, B | nf-core CLI only. |
| Do not edit `modules/nf-core/**` without `nf-core modules patch` | PATH-A, B | Unpatched edits silently overwritten. |
| Do not run `nf-core modules install` | PATH-C | No infrastructure files present. |
| Do not use `nf-core schema build` without `--no-prompts` | PATH-A | Use `--no-prompts` to avoid an interactive browser session. |
